Web Developer

2022 - present

Auditoría General de la Provincia de Salta - professional, full time

What they do

The provincial audit office receives the annual financial accounts of every municipality in Salta, stores them, checks them, and turns them into the statistics the province publishes. My work is the software half of that: collecting the data, storing it, providing auditors a comprehensive UI to audit it and showing it in an easily digestible way to the public.

The system, module by module

One application carries the whole life of a municipal account, which is the clearest way I have found to show how much is really in there:

  • Institutional accounts, and the documents filed against them.
  • Expedientes: the process itself and everything attached to it.
  • Audits: running them, and the trail of everything that happened along the way.
  • Work programs: planning who audits what, and when.
  • Documents and files, handled with the care an official record deserves.
  • Jurisdictions: what each office is allowed to see and to do.
  • Legal notifications by e-mail, plus a live channel for the ones that should not wait.

What I built

  • An internal system to submit, store and search municipal financial data for the current and previous years, and to generate the province-wide statistics that come out of it.
  • A full audits module: work programs, the audits themselves, and generating the final reports the office signs off on.
  • A public-facing web application so anyone can look at the collected data in a form that is actually readable, instead of asking the office for a copy of a PDF.
  • A municipal communication application that replaced physical (paper/mail) submissions with digital ones, with national file signature validation so a submission can be traced and trusted.
  • The plumbing in between: the MySQL schema, the Spring Boot API, the deployment on AWS, and the boring parts of the app that keep the auditors from filing tickets.

The parts that were not simple

Files big enough to hurt

A client side view of a mostly backend problem.

A municipal account and the system's notifications arrive with PDF files the size of a small hard drive, and every one of them has to be checked before it counts for anything. The application server cannot be the thing that carries them, so the browser sends the file straight to storage using an address the backend signs, and the backend only ever deals with metadata. There are two flows, and the interface had to cover both:

  • For files that can be checked in the background: upload, confirm, then watch it move through pending → validating → valid/invalid → done. The screen follows that state instead of guessing at it, and says something useful when a file comes back rejected.
  • For files a form needs before it can be saved: the upload happens first, the form then refers back to it by its id, and the server only moves the file into its permanent home once every check passes. When something fails, the form stays filled in and the upload can be retried instead of retyped.
  • Temporary uploads expire on their own, so an abandoned file does not sit in storage forever.
Screens that stopped feeling fast

The backend had the queries; this is what the interface did about it.

Office staff live in the listing screens, so those are the ones that quietly stop feeling fast once there are thousands of accounts behind them. The fixes were shared with the backend, which took the queries and the shape of the answers; my half was:

  • Keeping the reference data that does not change between visits out of the way, so opening an account does not re-fetch the list of jurisdictions, document types and audit states every single time.
  • Knowing the difference between a list and a detail request, and asking for only the fields the screen is actually going to show.
  • Letting the browser reuse what it already has, so a screen that has not changed answers with “nothing new” instead of the whole body all over again.
  • Keeping the big tables usable while they load, instead of a spinner in front of an empty page.

My role

  • Frontend-heavy full stack: React and Tailwind on top of a Spring Boot API and a MySQL database I also designed.
  • The whole visible surface of the product: the screens the office works in every day, the forms the municipalities file, and the public site that publishes the result.
  • Translator between the auditors and the code. Most of my best requirements arrived as paperwork, and my job was to work out what the screen should be.
  • Shipped in small pieces, in production, for real users, while the old process kept running alongside.
  • Handled the parts nobody asks for: input validation, audit trails, permissions, and not losing anybody's data.
